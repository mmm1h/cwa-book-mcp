# 技术栈与内存预算

本页是技术选型和资源门槛的唯一详细定义。内存数字是工程目标；实际测量结果单独记录在 docs/benchmarks。

## 技术栈

| 层 | 选择 | 理由与限制 |
| --- | --- | --- |
| 语言 / 编译器 | Go 1.27.2，go.mod、Dockerfile 和 CI 精确固定 | 复用书源核心，单二进制，避免解释器常驻；升级后重新验证 |
| MCP | 官方 modelcontextprotocol/go-sdk v1.8.0 | Streamable HTTP，复用协议与 schema 支持 |
| HTTP | net/http、标准库 TLS、CookieJar | 不加 Gin/Fiber 等 Web 框架 |
| 书源 | heartleo/zlib 的 Go 包 | 优先导入核心库，不启动 CLI/TUI |
| CWA | 自写小型 HTTP adapter | 复用 OPDS 与网页上传流程，不复制 CWA 实现 |
| 持久化 | go.etcd.io/bbolt v1.5.0 | 单进程嵌入式 KV，无独立数据库和 CGo 依赖 |
| 编解码 | encoding/json、encoding/xml | OPDS 流式解析；HTML 表单只解析受限响应 |
| 日志 | log/slog | 结构化、脱敏；不引入常驻遥测服务 |
| 交付 | Linux amd64/arm64 单二进制和精简镜像 | 运行镜像保留 CA 证书，非 root 运行 |

不使用 Python、Node.js 应用运行时、浏览器、n8n、Redis、Postgres、全文搜索引擎或另一个转换程序。开发测试优先 Go；仓库校验可用 Go 或平台自带 shell，不引入 Python 工具链。

bbolt 优于当前需求下的 SQL 层，是因为只需要任务、幂等键和少量索引；它不自动保证低内存。它会 mmap 文件，必须同时控制数据保留和测量 RSS。未来若需要关系查询，先提供真实需求和基准再改变选型。

## 依赖固定与复用边界

P0 已验证并固定上述版本，提交 go.mod/go.sum。书源核心固定 `6a299fdc59927f7e84f94390c4e54bfaf4d06cee`，最小补丁见 [PATCHES](../third_party/zlib/PATCHES.md)；不在运行或构建时盲目追 latest。

heartleo/zlib 的调研基准见 [研究证据](../docs/research/upstream-audit.md)。其模块包含 CLI/TUI 依赖，不代表导入核心包一定链接它们；用 go list -deps 和构建结果确认，不按 go.mod 行数猜测内存。

已发现的书源风险：

- 部分元数据请求使用无明确大小上限的 ReadAll。
- 搜索接口并非全部接收 context，默认 HTTP 超时也不等于本项目工具超时。
- 下载可以流式处理，但文件限制、暂存完整性与总体截止时间仍要由适配层保证。

P0 必须落实响应大小、取消与超时的真实控制。如果所固定版本没有合适扩展点，允许只对 MIT 书源库做最小、可审计的适配补丁或 vendor 修正，并保留许可证与基准提交记录；这不授权修改 CWA。禁止用反射改私有字段，禁止只让外层 goroutine 超时返回却任由底层请求持续累积。

## 内存发布门槛

基准：Linux amd64，单实例，默认并发，1,000 条保留任务，固定构建和 GOMEMLIMIT=64MiB。arm64 需要单独实测；没有运行条件时可以交付交叉编译产物，但必须标注“未完成 arm64 资源验收”，不能把 amd64 数据当作证明。

| 指标 | 门槛 |
| --- | --- |
| 启动预热后空闲 5 分钟的进程 RSS | ≤ 32 MiB |
| 规定混合负载的进程峰值 RSS | ≤ 96 MiB |
| 容器 memory.max | 128 MiB 下完成规定负载且无 OOM |
| 小文件与 1 GiB 合成文件的峰值 RSS 差值 | ≤ 16 MiB，不能随文件体积线性增长 |
| 固定规模任务集的持续测试 | 无持续增长的 goroutine、FD、活跃定时器或未释放请求 |

GOMEMLIMIT 是 Go 运行时软限制，不能限制全部 RSS、mmap、内核缓冲或文件页缓存。不能用 HeapAlloc 冒充 RSS，也不能只看 docker stats 的单点读数。

同时记录 VmRSS/VmHWM、Go heap、goroutine、FD、cgroup memory.current/memory.peak 和 memory.stat 中的 anon/file。书籍暂存产生的页缓存必须计入容器压力测试；容器门槛和 RSS 门槛分别验收。

不达标时先分析分配与资源生命周期。未经明确决策不得把 128 MiB 改成 512 MiB 来让验收通过。

## 默认资源上限

| 资源 | 初始默认值 |
| --- | --- |
| 活跃书源获取/CWA 提交 worker | 1 |
| 同时进行的书源元数据请求 | 1；账号登录状态串行保护 |
| 同时进行的文件传输 | 2（全局共享上限） |
| 同时执行的控制请求 | 8，超出返回可重试的繁忙状态 |
| 未结束任务 | 32，超过拒绝新增 |
| 流复制缓冲 | 每传输 64 KiB，池有固定上界 |
| MCP 控制请求体 | 256 KiB |
| 单次工具结果 | 128 KiB，默认 20 个候选，上限 50 |
| OPDS/书源元数据响应 | 解压后 4 MiB，压缩前也设上限 |
| 单次搜索分页预算 | CWA、书源各最多 3 页；同渠道的不同语言查询共用预算，未查完标记 incomplete |
| 控制查询 / 单次元数据请求 | 总计 30 秒 / 每请求 10 秒，上游请求受调用 context 取消 |
| 单次文件传输 | 最长 30 分钟，读写停滞 60 秒中断；按传输实现截止时间，不套用元数据超时 |
| 单文件大小 | 默认 512 MiB，可配置；测试时允许 1 GiB |
| 全部暂存文件 | 默认 4 GiB，并保留磁盘余量 |
| 候选与分页上下文 | 最长 30 分钟；候选至多 1,000 条、分页上下文至多 100 条，仅存受限元数据 |
| 上传 / 下载票据 | 15 分钟 / 10 分钟内可开始请求；已开始传输受独立传输截止时间控制 |
| 未结束任务最长存活 | 创建后 24 小时，含 awaiting_upload、blocked、needs_review；到期 cancelled / TASK_EXPIRED |
| 已结束任务历史 | 最多 1,000 条且最长 7 天，先到者清理 |
| ready 后暂存书籍 | 验收完成即清理；中断清理在启动时补做 |
| failed / cancelled 后暂存书籍 | 清理，不再恢复终态；仍可重试的任务留在非终态并受 24 小时总寿命约束 |

上限是协议和实现的一部分。所有队列、缓存、响应、重定向、重试和轮询必须有界。候选缓存不保存页面正文；分页游标不可把无限候选塞进响应。

暂存配额包括设备上传预留、源文件、.part 文件和 CWA 验证副本；不能只统计已完成文件。接收前预留容量，结束后释放。1 GiB 测试覆盖流传输与完整校验，控制响应仍保持原来的小上限。

候选与分页上下文持久化在 bbolt，到期或达到数量上限时有界清理；任务创建时复制所需候选快照，因此后续候选过期不会使已接受任务失效。未结束任务到期后释放队列名额；幂等记录随对应任务历史清理。

512 MiB 是应用可配置的默认文件上限，不代表 Cloudflare 或 CWA 通路允许该大小。实际接入须按 [运维设计](../docs/operations.md) 收紧。

## 流式实现规则

- 下载到磁盘；CWA multipart 上传使用文件流和 io.Pipe，禁止 bytes.Buffer 拼整本书。
- 本地上传使用请求流或 MultipartReader，避免 ParseMultipartForm 的默认内存驻留。
- 不通过 MCP 返回 base64 书籍，不使用 os.ReadFile/io.ReadAll 读取整本书。
- ZIP/EPUB 检查设置条目数、元数据大小和解压量上限；不把整本书解压进 RAM。
- 请求失败、提前返回、取消和超限都关闭 body、文件和管道。
- 复用有界 HTTP transport；不为每次轮询创建客户端或无限连接池。
- bbolt 事务不跨网络等待，按批读取到期任务，不在启动时把全部记录加载到内存。
- 清理历史和暂存文件有上限；数据库压缩作为独立维护操作，不与文件峰值传输并行。
- 首版不常驻运行 pprof 对外端点；开发分析显式启用，资料只保存到被忽略的目录。

## 基准工作负载

使用本地受控书源和 CWA 替身，避免外部站点速度干扰：

1. 同时存在一个服务端获取任务与一个客户端下载或上传。
2. 交错发送 20 个有界搜索/状态请求，验证背压。
3. 分别传输 10 MiB、100 MiB、1 GiB 合成文件，校验完整哈希。
4. 加入慢接收端、断开、重试、额度错误、上传结果未知和重启。
5. 完成至少 100 个顺序任务并进行 30 分钟稳定性测试。
6. 单独跑 -race 测试；性能门槛使用普通发布构建，不混用 race 开销。

记录硬件、架构、Go/依赖版本、构建参数、样本大小、并发、采样方法和原始汇总数据，写入 docs/benchmarks。实测结果与本页的目标数字分别维护。
